# CodeBase Agent 改进路线图：Demo → 影子模式 → 生产

> 目的：把这个"能自己用"的工具，按可度量的方式逐步推进到"可信、可持续改进、可对外"的产品。
> 原则：先能观测、再谈优化；先零风险验证（影子），再小范围灰度，最后全量。

---

## 1. 现状评估

| 维度 | 状态 | 说明 |
|---|---|---|
| 功能闭环 | ✅ MVP+ | 仓库分析（Python/Go）、混合检索（向量+BM25+RRF）、问答、双窗口、历史检索、文件查看、依赖图（4 视图）、PR 分析（中文+AI 总结）、移动端 |
| 工程质量 | ⚠️ 早期 Beta | 有零散单测；缺 CI、集成/E2E；缺可观测性 |
| 安全 | ❌ 未达可公开 | 默认无鉴权，却已用域名公网暴露；无限流 |
| 运维/数据 | 🟡 原型级 | 单机单进程、本地 SQLite/Chroma、无迁移/备份/多租户 |

**阶段判定**：个人自用 MVP，功能接近 Beta；**对外 = 早期内测**。

**当前最大风险**：公网无鉴权 → 任何人可消耗 LLM 配额、查看历史。

---

## 2. 阶段定义

- **Demo**：能跑通、能演示；无法量化质量。
- **影子模式（Shadow）**：真实使用，**只观察不接管**。记录每次问答的决策链与结果，人工对照，零风险验证可靠性。
- **灰度（Canary/Beta）**：少量真实用户使用；有鉴权/限流/备份；监控与回滚就绪。
- **生产（Production）**：稳定 SLA、可观测、可回滚、可持续迭代。

---

## 3. 路线图总览

| 阶段 | 目标 | 关键产出 | 验收 |
|---|---|---|---|
| Stage 0 Demo（现状） | 功能闭环 | 现有功能 | 能跑通 |
| Stage 1 影子地基 | 看得见好坏 | Query Trace、指标、反馈、端到端评测 | 每次问答可追溯；指标页可看；好评率/命中率可量化 |
| Stage 2 影子运行 | 真实场景验证 | 1–2 周真实记录 + 周报 | 周报含指标与坏例；无阻断级问题 |
| Stage 3 对比调优 | 提升质量 | 坏例驱动的检索/prompt/模型调优 | 回归评测不退化，关键指标上升 |
| Stage 4 灰度/生产前置 | 可安全对外 | 鉴权、限流、备份、监控、部署自动化 | 安全清单通过；可回滚 |
| 持续改进 | 长期迭代 | 每周 指标→坏例→改→评测→发布 | 指标持续向好 |

## 4. Stage 1：影子模式地基（优先）

### 4.1 Query Trace（每次问答一条结构化记录）
字段建议：
- `ts`、`repo`、`conversation_id`、`pane`(overview/detail)
- `question`、`route`(exact/semantic/overview)、`overview`(bool)
- `retrieved`: `[{name, file_path, score}]`
- `context_chars`、`context_tokens_est`
- `llm_model`、`llm_latency_ms`、`llm_ok`、`llm_error`
- `answer_len`、`cost_est`
- `fallback`（是否 Redis/缓存命中、是否降级）

落库：SQLite `query_traces` 表（或 JSONL 文件）。

### 4.2 指标（指标页 / 周报）
- 成功率（HTTP 200 / 总请求）
- 检索命中率（评测集 top-k）
- **答案质量**（人工 👍/👎 好评率）
- 延迟 P50/P95（端到端、LLM 单独）
- token/成本（估算）
- LLM 错误分布（401/403/429/超时/其他）

### 4.3 答案反馈
- 每条 AI 回答下加 👍/👎（写入 `answer_feedback` 表，关联 trace）。
- 支持一句备注（可选）。

### 4.4 端到端评测
- 固定数据集：`evaluation/data/*_qa.json` 扩展为"问题 + 期望文件/函数 + 参考答案要点"。
- 跑分脚本输出：检索命中率、答案要点覆盖率、延迟、成本。
- 用作**回归基线**：任何改动前后对比。

**验收**：任取一次线上问答，能从 trace 还原"召回了什么、用了多少上下文、模型耗时、是否失败"；指标页能看 7 天汇总；👍/👎 能落库。

---

## 5. Stage 2：影子运行
- 真实使用 1–2 周，系统**只记录、不接管决策**。
- 每周产出：指标汇总 + Top10 坏例（低分/失败/慢/贵）。
- 不做大改，只收集证据。

---

## 6. Stage 3：对比调优
按坏例分类处理：
- 检索不中 → 调 chunk/embedding/BM25 权重/RRF。
- 答非所问 → 调 prompt、上下文组织、few-shot。
- 模型/成本 → 换模型、调温度、限上下文。
每次改动：**改 → 跑评测 → 对比基线 → 通过才发布**。

---

## 7. Stage 4：灰度 / 生产前置（安全与运维）
- **鉴权**：Cloudflare Access 或应用内登录（二选一，必须先上）。
- **限流**：按 IP/会话限速，防刷。
- **备份**：`data/history.db`、`data/chroma`、`data/cache` 定期备份 + 恢复演练。
- **密钥**：`.env` 不入库；轮换机制。
- **监控/告警**：错误率、延迟、LLM 失败突增。
- **部署**：Docker 镜像更新 + 一键启动（应用 + 隧道）；可回滚。
- **数据生命周期**：仓库/索引/会话的删除与重建入口（已有 `DELETE /repos/{name}`）。

---

## 8. 度量体系（定义）

| 指标 | 定义 | 目标（初期） |
|---|---|---|
| 成功率 | 2xx / 总请求 | ≥99% |
| 检索命中率 | 评测集 top-3 命中期望文件 | ≥70% |
| 好评率 | 👍 / (👍+👎) | ≥80% |
| 端到端 P95 | 问答响应时间 | ≤30s |
| LLM 错误率 | 失败调用 / 总调用 | ≤2%（除配额外） |
| 单次成本估算 | token × 单价 | 设预算上限 |

---

## 9. 持续改进闭环（每周）
1. 看指标（对比上周）。
2. 抽 10 条坏例定位根因（检索 / 上下文 / 模型 / 环境）。
3. 选 1–3 个最高价值问题修。
4. 跑回归评测，确认不退化。
5. 发布 + 记录变更（CHANGELOG）。
6. 回到 1。

---

## 10. 工程与质量
- **测试分层**：单元（纯逻辑）→ 集成（parse+index+query，用 mock LLM）→ E2E（可选）。
- **CI**：push 触发 lint + 单测 + 评测基线。
- **可观测性**：结构化日志 + trace 表 + 指标页。
- **错误处理**：边界处统一异常与降级（已有全局 handler）。

---

## 11. 数据与生命周期
- SQLite 已开 WAL；补 `query_traces` / `answer_feedback` 表与索引。
- Chroma：集合命名规范；仓库删除时同步删集合。
- 缓存：`repo_cache` 按文件指纹；清理策略。
- 备份/迁移：版本化 + 恢复脚本。

## 12. 优先级与里程碑

| 优先级 | 事项 |
|---|---|
| **P0（现在）** | Query Trace、👍/👎 反馈、指标汇总页；**公网鉴权**（若对外） |
| **P0** | 备份（history.db/chroma）+ 恢复演练 |
| **P1** | 端到端评测 + CI；限流；LLM 超时/重试/降级完善 |
| **P1** | 监控告警；Docker/部署自动化 + 文档 |
| **P2** | 多用户/多租户；并发与索引缓存；成本预算与告警 |

---

## 13. 风险登记
- 公网无鉴权被滥用（立即处理）。
- LLM 供应商配额/权限波动（已遇 403/429）→ 多供应商/降级。
- 索引/嵌入模型更换导致质量回退 → 评测基线把关。
- 本地文件无备份导致历史/索引丢失。
- 单机停机即服务不可用 → 明确"自用工具"定位或上云。
